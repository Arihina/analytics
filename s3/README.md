# Альтернативы MinIO: self-hosted S3-хранилища
### (актуально на момент октября 2026 года)

## Ceph RGW

Лицензия: LGPL. Объектный шлюз поверх кластера Ceph (RADOS), который также даёт блочное и файловое хранилище.

### Преимущества
- Самая полная поддержка S3 среди рассматриваемых вариантов.
- Erasure coding, репликация, самовосстановление.
- Масштабирование до петабайт и сотен узлов.
- Multisite-репликация между зонами и ДЦ.
- Единая платформа: объект, блок и файл в одном кластере.

### Недостатки
- Высокая сложность и крутая кривая обучения.
- Высокие требования к железу и сети.
- Избыточен для небольших объёмов.
- Для надёжной работы нужно минимум 3 узла, на практике 5 и больше.

### Для каких нагрузок лучше всего подходит
- Крупные корпоративные хранилища.
- Бэкапы и архивы большого объёма (в том числе с Object Lock).
- Big data и data lake.
- Смешанные нагрузки, когда кроме S3 нужны RBD или CephFS.

### Степень совместимости с S3
**Очень высокая.** Документация Ceph перечисляет как поддерживаемые: bucket lifecycle, политики и ACL, версионирование, нотификации, multipart, тегирование, storage classes, POST Object. Ограничения:
- репликация бакетов частичная, только между зонами;
- набор canned ACL отличается от AWS;
- экзотика AWS (Object Lambda, Inventory, Analytics, Intelligent-Tiering): оценка, не реализована, проверять по версии.

### Сложность развертывания и эксплуатации
**Высокая.** Развёртывание через cephadm или Rook (Kubernetes). Сложные обновления, тюнинг, диагностика. Требует продуманного планирования (CRUSH-карта, пулы, сеть).

## SeaweedFS

Лицензия: Apache 2.0. Написан на Go. Изначально сделан для эффективного хранения мелких файлов (идеи из Facebook Haystack), позже получил filer, S3-шлюз, erasure coding и интеграцию с облаком.

### Преимущества
- Отлично работает с огромным числом мелких объектов.
- Лёгкий, запускается от одного узла (`weed server -s3`).
- Erasure coding для тёплых данных, репликация на уровне томов.
- Асинхронная репликация и tiering в облако.
- Широкий S3 API, включая версии, Object Lock, IAM API, SSE, S3 Tables (Iceberg).

### Недостатки
- Несколько компонентов: master, volume-серверы, filer, S3-шлюз.
- Filer требует внешнюю БД метаданных, которую нужно резервировать и мониторить. Потеря метаданных равна потере доступа к данным.
- Топологию (репликация, стойки, ДЦ, размеры томов) нужно продумать заранее, менять её потом сложно.
- Документация фрагментарная.
- Для очень крупных объектов нагрузка может смещается в метаданные.

### Для каких нагрузок лучше всего подходит
- Миллионы и сотни миллионов мелких объектов (оценка: от сотен байт до нескольких МБ).
- Медиа, логи, артефакты, ML-датасеты.
- Edge и распределённые развёртывания.
- Смешанные нагрузки, где нужен также доступ через файловый интерфейс (filer, FUSE).

### Степень совместимости с S3
**Высокая.** Реализованы lifecycle (без transition-правил), versioning, Object Lock, CORS, bucket policies, SSE, IAM API. Не поддерживается S3 Object Lambda (WriteGetObjectResponse).

### Сложность развертывания и эксплуатации
**Средняя.** Быстро стартует (Docker, Helm, один бинарник), но продакшен-развёртывание требует HA для master и filer, отказоустойчивой БД метаданных и продуманной топологии.

## Garage

Лицензия: AGPLv3. Написан на Rust. Минималистичное распределённое S3-хранилище, рассчитанное на кластеры из недорогого железа в нескольких локациях.

### Преимущества
- Один бинарник, минимум ресурсов.
- Простая настройка и эксплуатация.
- Работает на разнородных дисках и слабом железе.
- Устойчив к плохим и нестабильным сетям, поддерживает геораспределённость.
- Подходит для бэкапов, статики, хостинга сайтов.

### Недостатки
- Только репликация данных, без erasure coding (расход места x3).
- S3 намеренно урезан.
- Не рассчитан на высокий throughput.
- AGPL: важно учитывать, если предоставлять сервис наружу.

### Для каких нагрузок лучше всего подходит
- Малые и средние объёмы.
- Бэкапы через restic, rclone и подобные инструменты.
- Статические файлы, артефакты, логи.
- Домашние лаборатории и распределённые площадки.

### Степень совместимости с S3
**Базовая, намеренно урезанная.** Не реализованные API возвращают 501 Not Implemented.
- нет версионирования (GetBucketVersioning возвращает заглушку);
- нет ACL и bucket policies, вместо них собственная модель прав «ключ на бакет»;
- нет подписи SigV2, только SigV4;
- нет серверного шифрования (предлагается шифровать диск или шифровать на клиенте);
- lifecycle ограничен узким набором действий.

### Сложность развертывания и эксплуатации
**Низкая.** Один бинарник, простая конфигурация, минимальные требования. Для надёжности нужно 3 узла.

## RustFS

Лицензия: Apache 2.0. Написан на Rust. Позиционируется как прямая замена MinIO. Версия 1.0.0 вышла в GA 16 сентября 2026 (бета в апреле, RC в августе 2026).

### Преимущества
- Заявленная производительность и стабильное потребление памяти под нагрузкой.
- Permissive-лицензия (Apache 2.0).
- Модель, близкая к MinIO: просто мигрировать и использовать.
- Заявлены lifecycle, multipart, erasure coding, tiering, нотификации, мультиарендность, декомишнинг пулов.
- Поддержка OpenTelemetry, Docker и Kubernetes.
- Инструменты миграции с MinIO, включая чтение on-disk формата MinIO (preview).

### Недостатки
- Очень молодой проект.
- GA не означает отсутствие дефектов. Сами мейнтейнеры заявляют паритет только с core-функциями открытой версии MinIO.
- S3 Tables и Iceberg пока только preview.
- Данные MinIO с SSE-C или KMS нельзя мигрировать простой подменой бинарника.
- Распределённый режим долго считался сырым, его зрелость нужно проверять отдельно.
- Рекомендуется начинать с некритичных нагрузок и canary-развёртываний.

### Для каких нагрузок лучше всего подходит
- Высокопроизводительный S3 (AI/ML, аналитика).
- Мелкие объекты и ресурсоограниченные среды.
- Замена MinIO с минимальными изменениями в клиентах.

### Степень совместимости с S3
**Высокая по заявлениям, требует проверки.** Цель проекта паритет с открытой версией MinIO. Поддержка ключевых операций заявлена.

### Сложность развертывания и эксплуатации
**Низкая или средняя.** Развёртывание простое (бинарник, Docker, Kubernetes), эксплуатация близка к MinIO. 

## Apache Ozone

Лицензия: Apache 2.0. Проект Apache Software Foundation. Начинался в ветке HDFS-7240 внутри Hadoop для решения проблем масштабируемости HDFS, в октябре 2020 года стал отдельным top-level проектом ASF. Основной вклад идёт от инженеров Cloudera.

### Преимущества
- Масштабируется до миллиардов объектов.
- Нативная интеграция с экосистемой Hadoop (HDFS-совместимый интерфейс, Spark, Hive).
- Репликация и erasure coding, консенсус на Raft (Apache Ratis).

### Недостатки
- Тяжёлая архитектура: Ozone Manager, Storage Container Manager, Datanodes и S3 Gateway.
- Избыточен вне экосистемы Hadoop и больших данных.
- S3-слой вторичен по отношению к основному интерфейсу.
- Меньше практик использования как «просто S3-хранилища».

### Для каких нагрузок лучше всего подходит
- Data lake в окружении Hadoop и Spark.
- Аналитика и пакетная обработка больших данных.
- Замена HDFS с сохранением совместимости.

### Степень совместимости с S3
**Базовая или средняя (оценка).** Доступ через S3 Gateway.

### Сложность развертывания и эксплуатации
**Высокая.** Много компонентов, нужен опыт работы с Hadoop-экосистемой. Оправдано только если Hadoop или Spark уже есть в инфраструктуре.

## Краткое сравнение

| Хранилище | Совместимость с S3 | Сложность | Лучше всего подходит |
|---|---|---|---|
| Ceph RGW | Очень высокая | Высокая | Крупные универсальные кластеры, Object Lock, multisite |
| SeaweedFS | Высокая | Средняя | Много мелких файлов, медиа, ML-датасеты |
| Garage | Базовая (урезана) | Низкая | Бэкапы, статика, малые объёмы |
| RustFS | Высокая (под вопросом) | Низкая/средняя | Замена MinIO, высокий throughput |
| Ozone | Базовая/средняя (оценка) | Высокая | Data lake в Hadoop-окружении |
